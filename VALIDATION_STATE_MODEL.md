# Раздельная модель состояния выполнения и метрологической оценки

## 1. Назначение документа

Документ фиксирует правила проверки отдельных измерений, поверочных точек и прибора после разделения состояния выполнения и метрологического результата. Он является руководством для разработчиков модели, машины измерения, репозиториев, UI и экспорта.

Для каждого объекта необходимо рассматривать **четыре независимых значения**:

| Значение | Назначение |
|---|---|
| `Status` | Что происходит с объектом в процессе измерения и сохранения. |
| `Validation` | Итог метрологической оценки. |
| `ValidationReason` | Формализованная причина итога. |
| `ValidationMessage` | Краткое фактическое пояснение с измеренными и допустимыми значениями. |

`Status` не является результатом поверки. Порядковый номер элемента любого перечисления запрещено интерпретировать как элемент другого перечисления.

---

## 2. Общий метрологический итог

`EValidationStatus` используется одинаково на всех трёх уровнях:

| Значение | Смысл |
|---|---|
| `vsNone` | Анализ ещё не выполнялся. |
| `vsUndefined` | Анализ выполнялся, но данных недостаточно для ответа «годен/не годен» либо измерение нельзя учитывать. |
| `vsValid` | Объект годен. |
| `vsInvalid` | Объект не годен. |

`vsNone` и `vsUndefined` не взаимозаменяемы. После попытки анализа без достаточных данных должен быть установлен `vsUndefined`, а не `vsNone`.

## 3. Отдельное измерение `TPointSpillage`

### 3.1. Состояние выполнения

`EMeasurementSpillageStatus` содержит только этапы жизненного цикла измерения:

- `mssNone` — состояние не задано;
- `mssCreated` — объект измерения создан;
- `mssDataAssigned` — исходные данные присвоены;
- `mssAnalyzing` — выполняется метрологический анализ;
- `mssCompleted` — анализ измерения завершён;
- `mssSavePending` — ожидается сохранение;
- `mssSaved` — измерение сохранено;
- `mssInterrupted` — выполнение прервано;
- `mssCancelled` — результат отменён;
- `mssError` — ошибка выполнения или миграции.

### 3.2. Причины метрологического результата

| Причина | Ожидаемый итог | Назначение |
|---|---|---|
| `svrNone`, `svrNotAnalyzed` | `vsNone` | Анализ не выполнялся. |
| `svrDisabled` | `vsUndefined` | Измерение отключено и не учитывается. |
| `svrPointNotMatched` | `vsUndefined` | Расход не соответствует поверочной точке. |
| `svrStopCriteriaFailed` | `vsUndefined` | Не выполнен критерий остановки. |
| `svrInvalidSourceData` | `vsUndefined` | Исходные данные непригодны для оценки. |
| `svrErrorExceeded` | `vsInvalid` | Фактическая погрешность превышает допустимую. |
| `svrErrorWithinTolerance` | `vsValid` | Фактическая погрешность находится в допуске. |

### 3.3. Порядок анализа

`TDevice.AnalyseDataPoint` выполняет проверку в следующем порядке:

1. Назначает измерению UUID прибора и переводит выполнение в `mssAnalyzing`.
2. Ищет поверочную точку существующим `FindMatchedDevicePointForSpillage`/`IsFlowInPoint`.
3. При отсутствии точки устанавливает `vsUndefined + svrPointNotMatched`.
4. Выбирает критерии остановки точки, затем прибора; при пустом наборе применяется критерий времени.
5. Проверяет импульсы, объём/массу и время в порядке, заданном кодом.
6. При невыполненном критерии устанавливает `vsUndefined + svrStopCriteriaFailed` и записывает фактическое и требуемое значения в `ValidationMessage`.
7. Не изменяя формулу `TPointSpillage.Error`, сравнивает `Abs(Error)` и `Abs(DevicePoint.Error)`.
8. При превышении устанавливает `vsInvalid + svrErrorExceeded`.
9. В пределах допуска устанавливает `vsValid + svrErrorWithinTolerance`.
10. После анализа состояние выполнения становится `mssCompleted`.

Совместимое свойство `Valid` доступно только для чтения и вычисляется как `Validation = vsValid`. Запись в него запрещена.

### 3.4. Цвет измерения

- `vsValid` — зелёный (`COLOR_COMPLETED`);
- `vsInvalid` — жёлтый (`COLOR_WARNING`), поскольку одно негодное измерение ещё не определяет итог всей точки;
- `vsNone` и `vsUndefined` — без цвета.

## 4. Поверочная точка `TDevicePoint`

### 4.1. Состояние выполнения

`Status: EMeasurementPointStatus` принадлежит машине измерения и описывает выбор точки и эталона, установку, стабилизацию, запуск, измерение, чтение, сохранение, завершение, пропуск, отмену и ошибки.

Методы метрологического анализа **не изменяют** `TDevicePoint.Status`. Владельцем переходов остаётся `TMeasurementRun`.

### 4.2. Причины результата точки

| Причина | Ожидаемый итог |
|---|---|
| `pvrNone`, `pvrNotAnalyzed` | `vsNone` |
| `pvrDisabled` | `vsUndefined` |
| `pvrNoMeasurements` | `vsUndefined` |
| `pvrNoMatchedMeasurements` | `vsUndefined` |
| `pvrInsufficientMatchedMeasurements` | `vsUndefined` |
| `pvrInsufficientValidMeasurements` | `vsInvalid` |
| `pvrRequiredValidMeasurementsCollected` | `vsValid` |
| `pvrInvalidSettings` | `vsUndefined` |

### 4.3. Формирование списков

`FillDataPointsList` сохраняет назначение двух списков:

- `DataPoints` — все включённые, не удалённые измерения активной сессии, сопоставленные с точкой;
- `ProtocolDataPoints` — отсортированный по модулю погрешности список кандидатов для протокола.

`ProtocolDataPoints` не является источником метрологического результата. Результат рассчитывается по `DataPoints`.

### 4.4. Счётчики и агрегирование

Для включённой точки рассчитываются:

- `RequiredCount` — `RepeatsProtocol`, но не менее одного;
- `MatchedCount` — количество включённых, не удалённых и пригодных для оценки измерений (`Validation` равен `vsValid` или `vsInvalid`);
- `ValidCount` — количество измерений с `vsValid`;
- `InvalidCount` — количество измерений с `vsInvalid`.

Порядок принятия решения обязателен:

```text
если ValidCount >= RequiredCount:
    vsValid + pvrRequiredValidMeasurementsCollected
иначе если MatchedCount < RequiredCount:
    vsUndefined + pvrInsufficientMatchedMeasurements
иначе:
    vsInvalid + pvrInsufficientValidMeasurements
```

Следствие: отдельное негодное измерение не делает точку негодной, если требуемое количество годных измерений уже набрано.

`ResultError`, `AverageError` и `StdDev` рассчитываются отдельно от выполнения точки. `ValidationMessage` содержит количества годных, негодных и требуемых измерений.

### 4.5. Цвет точки

- `vsValid` — зелёный;
- `vsInvalid` — красный;
- `vsNone` и `vsUndefined` — без цвета;
- цвет выполнения точки определяется отдельно функцией `GetPointExecutionStatusColor`.

## 5. Прибор `TDevice`

### 5.1. Состояние выполнения

`EMeasurementDeviceStatus` описывает подготовку, измерение, завершение, ожидание сохранения, сохранение, прерывание, отмену и ошибку. `TDevice.AnalyseResults` не изменяет это состояние.

### 5.2. Причины результата прибора

| Условие | `Validation` | `ValidationReason` | Цвет |
|---|---|---|---|
| Поверочные точки отсутствуют | `vsUndefined` | `dvrNoPoints` | без цвета |
| Нет включённых точек | `vsUndefined` | `dvrNoEnabledPoints` | без цвета |
| Все включённые точки годны | `vsValid` | `dvrAllPointsValid` | зелёный |
| Есть негодные, все точки определены | `vsInvalid` | `dvrInvalidPointsAndComplete` | красный |
| Есть негодные и неопределённые | `vsInvalid` | `dvrInvalidPointsAndIncomplete` | жёлтый |
| Негодных нет, часть точек не определена | `vsUndefined` | `dvrPointsIncomplete` | без цвета |

При агрегировании отключённые точки полностью исключаются. Завершённость результата определяется причиной: `dvrInvalidPointsAndComplete` означает окончательный негодный результат, а `dvrInvalidPointsAndIncomplete` — негодный промежуточный результат при незавершённой проверке.

## 6. Атомарная установка результата

Каждый класс предоставляет собственный `SetValidation`:

- устанавливает `Validation`, `ValidationReason` и `ValidationMessage` одной операцией;
- отвергает противоречивые пары, например `vsValid + svrErrorExceeded`;
- ничего не делает, если все три значения совпадают с текущими;
- при изменении переводит объект в `osModified`, инициируя одно модельное уведомление через существующий механизм состояния.

Клиентский код не должен изменять поля результата отдельно. Свойства результата доступны только для чтения.

## 7. Пользовательские тексты

Для каждого перечисления существует отдельная типизированная функция преобразования в русский текст. Для неизвестного значения возвращается диагностическая строка `Неизвестное состояние (код N)`.

Объекты предоставляют единый интерфейс:

- `GetShortStateText` — итог и существенная причина;
- `GetFullStateText` — состояние выполнения, результат, причина и фактическое пояснение.

Пустая причина или пояснение не выводятся. `GetEnumName` не применяется для пользовательского текста.

Пример полного текста:

```text
Состояние выполнения: Завершено.
Метрологический результат: не годен.
Причина: превышена допустимая погрешность.
Пояснение: Фактическая погрешность 1,240000 %, допустимая погрешность 1,000000 %.
```

## 8. Сохранение и совместимость

### 8.1. Старый формат измерения

Существующая таблица хранит версионно неразделённые поля `Status`, `StatusStr` и `Valid`. При чтении применяется только явная миграция `ImportLegacyValidation`:

| Старый код | Новый `Status` | Новый `Validation` | Причина |
|---:|---|---|---|
| 0 | `mssCreated` | `vsNone` | `svrNotAnalyzed` |
| 1 | `mssDataAssigned` | `vsNone` | `svrNotAnalyzed` |
| 2 | `mssCompleted` | `vsUndefined` | `svrPointNotMatched` |
| 3 | `mssCompleted` | `vsUndefined` | `svrStopCriteriaFailed` |
| 4 | `mssCompleted` | `vsInvalid` | `svrErrorExceeded` |
| 5 | `mssCompleted` | `vsValid` | `svrErrorWithinTolerance` |
| иной | `mssError` | `vsUndefined` | `svrInvalidSourceData` |

`StatusStr` переносится в `ValidationMessage`. Старый `Valid` передаётся только как дополнительный признак совместимости и не становится источником нового результата.

### 8.2. Запись в старую схему

Пока схема БД не имеет отдельных колонок и версии, обратное кодирование сосредоточено в `SpillageValidationToLegacyCode`. Оно используется только на границе репозитория и при формировании совместимого хеша. Runtime-код не использует старые числа.

Порядок ранее сериализуемых полей не изменён. Это позволяет читать существующие записи без неявного преобразования порядковых номеров новых перечислений.

---

## 9. Копирование объектов

- `TPointSpillage.Assign` копирует выполнение, результат, причину и сообщение вместе с измеренными данными.
- `TDevicePoint.Assign(..., FullAssign=True)` переносит runtime-состояние точки.
- `TDevicePoint.Assign(..., FullAssign=False)` копирует конфигурацию, но сбрасывает выполнение в `mptsNone`, результат в `vsNone`, причину в `pvrNotAnalyzed` и статистику в ноль.
- Синхронизация копии измерения в `TFlowMeter` использует `Assign`; отдельная запись в `Valid` больше не выполняется.

## 10. Ответственность компонентов

| Компонент | Ответственность |
|---|---|
| `TMeasurementRun` | Переходы `TDevicePoint.Status`. |
| `TWorkTable` | Выполнение сохранения измерения и прибора; не присваивает метрологический `Valid`. |
| `TDevice.AnalyseDataPoint` | `TPointSpillage.Validation*`. |
| `TDevice.AnalyseDevicePointsResults` | `TDevicePoint.Validation*` и статистика точки. |
| `TDevice.AnalyseResults` | `TDevice.Validation*`. |
| UI и экспорт | Только чтение готового состояния, текста и цвета. |
| Репозиторий | Явное преобразование старого формата на границе хранения. |

## 11. Изменения UI

UI должен использовать:

- `Validation` и `ValidationReason` для логики отображения;
- `GetShortStateText` и `GetFullStateText` для текста;
- `GetSpillageValidationColor`, `GetPointValidationColor`, `GetDeviceValidationColor` для результата;
- `GetPointExecutionStatusColor` только для состояния выполнения точки.

Получение состояния ячейки и отрисовка не вызывают `AnalyseResults` или `AnalyseDevicePointsResults` и не изменяют модель. В экспорт результатов передаётся вычисляемое значение `Valid`, поэтому старый формат выгрузки сохраняется без разрешения записи в модель.

## 12. Контрольный сценарий проверки

Для ручной или автоматизированной проверки необходимо пройти следующие случаи.

### Измерение

1. Новый объект: `mssCreated`, `vsNone`, `svrNotAnalyzed`.
2. Расход вне точек: `mssCompleted`, `vsUndefined`, `svrPointNotMatched`, без цвета.
3. Недостаточное время/объём/импульсы: `vsUndefined`, `svrStopCriteriaFailed`, фактические значения присутствуют в сообщении.
4. Погрешность выше допуска: `vsInvalid`, `svrErrorExceeded`, жёлтый.
5. Погрешность равна допуску: `vsValid`, `svrErrorWithinTolerance`, зелёный.
6. Повторный `SetValidation` с теми же аргументами не создаёт изменения.
7. Противоречивая пара результата и причины вызывает `EArgumentException`.

### Поверочная точка

1. `RepeatsProtocol = 0` требует минимум одно измерение.
2. Нет пригодных измерений: `vsUndefined`.
3. Пригодных измерений меньше требуемого количества: `vsUndefined`.
4. Пригодных достаточно, но годных недостаточно: `vsInvalid`.
5. Годных достаточно при наличии дополнительных негодных: `vsValid`.
6. Анализ не изменяет `EMeasurementPointStatus`.
7. `ProtocolDataPoints` не меняет результат при неизменном `DataPoints`.

### Прибор

1. Нет точек и нет включённых точек различаются причинами.
2. Отключённые точки не влияют на итог.
3. Все точки годны: зелёный итог `vsValid`.
4. Негодная точка при остальных определённых: красный итог.
5. Негодная и неопределённая точки: жёлтый итог.
6. Только неопределённые и годные точки: `vsUndefined` без цвета.
7. Анализ не меняет `EMeasurementDeviceStatus`.

### Хранение и копирование

1. Каждый старый код `0..5` мигрирует по таблице раздела 8.1.
2. Неизвестный старый код не приводится напрямую к enum.
3. Старое сообщение сохраняется в `ValidationMessage`.
4. Полное копирование переносит все четыре значения.
5. Конфигурационное копирование точки не переносит состояние чужого запуска.
6. Цикл чтение → анализ → запись сохраняет совместимость старой схемы и порядка хеша.

## 13. Глобальная проверка перед выпуском

Перед выпуском необходимо выполнить поиск по проекту:

```bash
rg -n "StatusStr|SPS_|BuildResultTextByStatus|ResolveDeviceSummaryStatus|GetStatusColor|AnalyseDataPoint|AnalyseDevicePointsResults|AnalyseResults|GetEnumName|EMeasurementPointStatus\\(|Ord\\(.*Status|\\.Valid\\s*:=" --glob '*.pas'
```

Каждое совпадение проверяется по фактическому типу объекта. Нельзя механически изменять независимые состояния `TSessionSpillage.Status`, `TFlowMeter.Status`, `TObjectState`, `EStableStatus`, `TMeterValueStabilityStatus`, `TWorkTable.State` и этапы `TMeasurementRun`.

Критерий готовности: ни один производитель или потребитель не использует порядковый номер состояния выполнения как метрологический результат; UI не пересчитывает модель; совместимость старых данных обеспечена явной функцией миграции.
